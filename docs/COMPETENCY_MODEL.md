# 现代研究程序员能力模型

本模型把 RCSL 的训练设计成两个互补维度：**纵轴判断最先失效的研究契约**，**横轴训练人类如何负责地使用 Agent 与证据**。它不是把所有能力排成更多关卡。

[English](COMPETENCY_MODEL_EN.md) · [案例发布模型](CASE_RELEASE_MODEL.md) · [四级框架](../skills/research-code-audit-training/references/four-level-framework.md)

## 先把模型用于自己的项目

准备一个 clean Git 目标项目，并在目标项目和本仓库之外创建本地证据工作区：

```bash
python scripts/rcsl.py audit init \
  --project /absolute/path/to/clean-git-project \
  --output /absolute/path/outside-project/my-audit \
  --level 1 --actor "declared owner label"
```

然后依次填写 [G0 研究契约](../skills/research-code-audit-training/assets/research-contract-template.md)、[快速分诊卡](../skills/research-code-audit-training/assets/triage-card-template.md)、[Human–Agent 委派合同](../skills/research-code-audit-training/assets/delegation-contract-template.md)和[证据护照](../skills/research-code-audit-training/assets/evidence-passport-template.md)。用 `python scripts/rcsl.py audit status /absolute/path/outside-project/my-audit` 查看生命周期状态，用 `python scripts/rcsl.py audit lint /absolute/path/outside-project/my-audit` 检查模板结构。两者都不判断内容是否科学正确。完整闭环见 [Mode Audit 指南](AUDIT_MODE.md)。

## G0：研究契约门（先于任何 Level）

G0 不是“Level 0 题目”，也不用于给候选排序。它是一道必须由人类研究负责人通过的门：在读取、生成、运行或比较候选之前，明确并冻结以下内容。

| 必须冻结的内容 | 最小可交付物 |
| --- | --- |
| 研究问题、允许的结论与不允许的外推 | `claim charter`：问题、目标、边界、成功与停止条件 |
| 论文、源码、数据与第三方材料的来源和许可范围 | 来源清单、允许读写路径、保护材料清单 |
| 数据切分、指标、baseline、预算和统计单位 | 可审计的实验协议与不变量 |
| Agent 能做什么、不能做什么、何时必须停下请求批准 | 委派合同、权限/预算矩阵、升级条件 |
| 隐私、安全、伦理和发布风险 | 风险登记、责任人、处置和披露规则 |

若 G0 不完整，正确动作是**暂停并请求澄清**，而不是让 Agent 根据默认值补写研究事实。

## 纵轴：以“首个失效契约”归类

一个错误可能造成多层后果，但应归入最先被破坏的契约。这样四级仍然是清晰、可复用的证据深度，而不是四个孤立主题。

| 纵轴 | 首个失效契约 | 人类必须能回答的问题 | 首选证据 |
| --- | --- | --- | --- |
| **L1 算法语义** | 公式、算子、索引、mask、loss 或梯度 | 这段可运行代码仍实现论文定义吗？ | 性质测试、极小张量、梯度探针 |
| **L2 流水线完整性** | 数据身份、状态、切分、评估或 checkpoint 流 | 这条样本/状态/指标链路始终一致吗？ | 跨产物血缘、独立重算、事件顺序 |
| **L3 科学有效性** | 比较设计、证据或 claim 范围 | 这组比较公平吗，证据支持到什么强度？ | 配置对照、账本重建、冻结分析规则 |
| **L4 Agent 实验治理** | 授权、审批、预算、记录或受保护证据 | 行动是否被授权且可追溯？ | 时间线、审批链、资源账本、报告审计 |

## 横轴：七项负责人能力

下表中的“人类负责”不能被静默委派；Agent 可以协助执行和提出候选，但不能替代最终责任。

| 能力 | 人类负责 | Agent 可在明确合同下协助 | 应留下的证据 |
| --- | --- | --- | --- |
| **C1 研究判断** | 定义问题、可接受风险、允许 claim 与最终结论 | 对齐论文/代码、列出冲突和未知项 | 研究契约、claim card |
| **C2 快速分诊** | 决定停止、隔离、升级、继续或标记未知 | 复现症状、汇总日志、执行受限探针 | 分诊卡：严重度、影响面、证据、下一安全动作 |
| **C3 委派与 Agent 保障** | 设定权限、预算、验收与升级点；批准关键改变 | 阅读、实现、测试、提取 trace、起草报告 | 委派合同与验收记录 |
| **C4 架构与可维护性** | 选择边界、接口、血缘、回滚与所有权 | 搭建模块、生成文档/测试、建议重构 | 架构决策记录、运行手册、变更历史 |
| **C5 安全、隐私与伦理** | 数据权利、披露、风险接受与例外批准 | 扫描密钥/依赖、识别不可信输入、生成威胁假设 | 安全案例：资产、信任区、风险、缓解与停止规则 |
| **C6 事故响应** | 宣布事故、暂停发布、通知、修复与关闭 | 保存日志、建立快照、复跑、起草复盘 | 事故账本、影响面、复盘与预防验证 |
| **C7 证据沟通** | 决定面向谁说什么、置信度和结论措辞 | 起草摘要、图表、引用追踪和技术翻译 | 决策备忘录：事实 / 推断 / 假设 / 建议 / 未知 |

### 所有 Level 共用的分诊循环

```text
发现 → 控制影响 → 确认影响面 → 收集最小决定性证据
→ 在明确边界内委派或升级 → 沟通决定与下一次检查
```

安全、隐私或伦理风险是**停线覆盖层**，不是等到 L4 才处理的收尾事项。即使尚未证明算法错误，只要发生敏感数据暴露、许可不明、受保护评价泄露或不安全外部操作，就应按 G0 的升级条件停止。

## 四档成熟度

成熟度描述同一能力的掌握深度，不创建新的 Level。学习者可以在 L1 达到 `Prove`，但在 L3 仍处于 `Recognize`。

| 档位 | 可观察行为 | 最低证据 |
| --- | --- | --- |
| **Recognize（识别）** | 在给定范围内识别风险或被破坏的契约，并说清不确定性 | 引用正确材料与检查清单 |
| **Prove（证明）** | 独立构造最小反例或可复现证据链 | 位置、契约、命令/产物、因果影响 |
| **Direct（指挥）** | 将工作拆给 Agent，限定权限，并审核其输出是否满足验收 | 委派合同、审查记录、升级决策 |
| **Steward（负责）** | 对风险、发布、claim 和事故关闭承担最终责任 | 批准/阻止决定、边界说明、面向相关方的记录 |

## 三条角色路线

路线是建议的练习顺序，不替代四级纵轴，也不意味着其他能力不重要。

| 路线 | 适用对象 | 推荐重点 | 典型产物 |
| --- | --- | --- | --- |
| **审计实践者** | 研究生、研究程序员、审稿协作者 | G0 + L1–L4；C1、C2、C7 | 每级一份 Evidence Passport：定位、规则、反例、影响、修复 |
| **研究系统维护者** | 维护数据/训练/评估系统的人 | G0、L1–L2；C2、C3、C4、C5、C6 | 血缘图、运行手册、分诊卡、事故复盘 |
| **研究负责人 / Agent 监督者** | PI、高年级研究者、研究工程负责人 | G0、L3–L4；C1、C3、C5、C6、C7 | 研究契约、审批记录、claim card、决策备忘录 |

## 下游 Capstone：跨契约研究事故

Capstone 不是 L5。它提供一个包含多层后果的案例，例如：局部语义偏差（L1）引发状态或切分污染（L2），漂亮结果被过度解读（L3），并且 Agent 在批准范围之外继续操作（L4）。

学习者必须：

1. 以 G0 判断是否立即停止和通知；
2. 用分诊循环保护证据、圈定影响面并安排委派；
3. 将每个问题按**首个失效契约**归类；
4. 生成技术事故报告和面向利益相关方的简明更新；
5. 修改协议、架构或运行手册，并证明预防措施被重新检查。

Capstone 的通过标准是可审计的决策与证据，而不是得到最高指标或“修好”一个文件。

## 与案例发布模型的关系

当前公开案例及其答案相关材料应作为 **Open Demo / honor isolation** 使用：学习者承诺在完成公开任务与证据记录前不查找教师材料，但公开仓库中的约定性隔离**不是安全边界**，不能声称为盲测、保密考试或对抗性防泄漏。

未来需要真正盲测时，采用 [Blind Challenge 分包建议](CASE_RELEASE_MODEL.md)；公开包、受控评测包和维护记录必须从一开始分开，不要把答案先提交到公开 Git 历史再试图隐藏。
